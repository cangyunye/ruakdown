```
BUG 定位与修复：

现象：斜杠面板/右键菜单中"提示块及以上"的条目（H1-H6、无序/有序/任务列表、引述块）在空行上选择后无任何输出；提示块及以下的条目正常。

根因（一条三元的布尔表达式）：planTogglePrefix 第 291 行
  const allHave = lines.every((l) => l.text.trim() === "" || hasMarker(l.text, spec));
空行被 trim 检查放行 → 单行空选区时 every 真空为真 → allHave=true → 走"移除标记"分支 → 空行没有可移除的标记（startsWith 失败、BLOCK_PREFIX 正则不匹配）→ changes 为空数组 → dispatch 空变更 = 无操作。
两类条目的差异：H1-H6/列表/引述用 togglePrefix（行前缀切换，命中此缺陷）；提示块/代码块/表格等用 insertBlock（块插入，空行本就正常）——用户截图里的分界线正是这两条代码路径的边界。

修复：移除判定改为"至少一行实际带标记"才成立：
  const allHave =
    lines.some((l) => l.text.trim() !== "") &&
    lines.every((l) => l.text.trim() === "" || hasMarker(l.text, spec));
保留了原意图（范围内空行不阻断移除），同时排除全空选区/单空行的真空真值。

影响面：该缺陷自一期右键菜单起就存在（同一套命令层），不是斜杠面板独有——右键菜单的空行 H1/列表同样修复。

验证：pnpm test 227/227（+5 空行前缀用例：空行加 H1 且光标落标记后、ul/ol/task/quote 四种标记、二次切换移除、空行+内容行混合添加、含尾空行范围的移除）、pnpm build 通过。
```

## 修复方案

修复 planTogglePrefix 的真空真值缺陷：allHave 从
  lines.every((l) => l.text.trim() === "" || hasMarker(l.text, spec))
改为
  lines.some((l) => l.text.trim() !== "") && lines.every((l) => l.text.trim() === "" || hasMarker(l.text, spec))
即"至少一行实际带标记"才走移除分支。原表达式在单空行/全空选区上真空为真，导致空行选择 H1/列表/引述时进入移除分支却无标记可移除、changes 为空、dispatch 空操作——这就是"提示块以上条目空行无效"的根因（提示块及以下用 insertBlock 块插入路径，不受影响）。修复后空行应用行前缀类条目正常插入标记且光标落在标记后，二次选择仍可切换移除。
验证：pnpm test 227/227（+5 空行前缀用例）、pnpm build 通过；同一命令层，右键菜单的同症状同步修复。

## 复盘

复盘：
1) 一行三元布尔表达式里混"真空真值"（every 对空集合/passed-through 元素恒真）是最隐蔽的一类缺陷：肉眼看逻辑"合理"，但改变了分支走向导致空操作。写"是否全部满足"这类判断时，先问一句"空集合/被豁免的元素会不会让它为真"。
2) 用户对缺陷边界的描述（"提示块以上的不行，以下的行"）直接指向了代码里的分界线——两条不同的实现路径（togglePrefix vs insertBlock）。按用户给出的边界去二分代码，比逐条试错快得多。
3) 先修交互层（上一轮的 IME/焦点问题）再看定位层：位置与命令契约用真实 EditorView 回归测试排除后，剩余可疑面收敛到命令内部的布尔逻辑，一击即中。
4) 空行/空集合是排版类命令的高频边界：补测试时把"空行"/"混合空行"/"含尾空行"作为固定用例族，成本低、防回归价值高。
